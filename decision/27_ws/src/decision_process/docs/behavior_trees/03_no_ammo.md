# 03 无弹量行为子树 NoAmmoBehavior

## 任务目标

比赛进行阶段中，当哨兵当前弹量为 `0` 时，立即停止射击并切换为移动姿态：有待领弹量则前往补给点 `(2,1)` 领取；没有待领弹量则返回选定的站桩点 `(4.971,7.5)` 等待。

## 输入与输出

| 类型 | 字段 | 用途 |
| --- | --- | --- |
| 输入 | `game_period` | 仅在比赛进行阶段 2 执行 |
| 输入 | `time` | 根据 420 秒倒计时计算已经结束的完整分钟数 |
| 输入 | `hp_sentry` | 哨兵存活时才执行移动 |
| 输入 | `ammo` | `0` 触发本行为；大于 `0` 时释放后续行为 |
| 输入 | 定位 `x、y` | 判断是否到达补给点或站桩点 |
| 内部状态 | `pending_ammo` | 根据时间累计、领取成功后清零的待领弹量估算值 |
| 输出 | `posture=3` | 无弹时使用移动姿态 |
| 输出 | `shoot_mode=0` | 无弹时强制停止射击 |
| 输出 | `tripod_mode=1` | 无弹移动或等待时继续转动云台观察 |
| 输出 | `target=0` | 清除之前遗留的自瞄目标 |
| 输出 | `/goal_pose=(2,1,1.0,map)` | 有待领弹量时前往补给点 |
| 输出 | `/goal_pose=(4.971,7.5,1.0,map)` | 无待领弹量时前往站桩点 |

## 待领弹量状态机

当前 `ReceiveData.msg` 只有实时 `ammo`，没有“待领取弹药数量”字段，因此需要在决策节点内维护状态。

```text
elapsed_seconds = 420 - clamp(time, 0, 420)
earned_grants = floor(elapsed_seconds / 60)
pending_ammo = (earned_grants - claimed_grants) * 100
```

| 剩余时间 | 已结束完整分钟 | 待领量（从未领取） |
| --- | --- | --- |
| 420～361 | 0 | 0 |
| 360～301 | 1 | 100 |
| 300～241 | 2 | 200 |
| 60～1 | 6 | 600 |
| 0 | 7 | 700 |

到达补给点后并不立刻在内部清零。`CollectPendingAmmo` 会停在补给点等待，只有裁判输入从 `ammo=0` 变为 `ammo>0`，才确认领取成功并令 `claimed_grants=earned_grants`。这样不会因为仅仅接近补给点就错误放弃待领弹量。

倒计时偶尔向上抖动时，已经获得的分钟次数不会减少。比赛离开阶段 2 后，在下一场重新进入阶段 2 时重置累计状态。

## 子树完整流程

```text
MainTree (ReactiveFallback)
├── NoAmmoBehavior
│   ├── GameRunning
│   ├── OutOfAmmo
│   ├── SetCombatIdle
│   ├── ApplyPosture(requested_posture=3)
│   └── CollectOrStandby (ReactiveFallback)
│       ├── CollectPendingAmmoSequence
│       │   ├── PendingAmmoAvailable
│       │   └── CollectPendingAmmo(2,1)
│       └── NavigateToPose(4.971,7.5)
└── OtherBehaviorsPlaceholder
```

`PendingAmmoAvailable` 放在站桩分支之前。一旦新的完整分钟结束，待领量从 0 变为 100，反应式回退节点会中止站桩导航并立即切换到补给点导航。

## 分支逻辑

```text
ammo > 0：
    本任务不执行，放行其他行为

ammo == 0 且 pending_ammo == 0：
    停止射击、清除目标、使用移动姿态
    前往站桩点 (4.971, 7.5)
    到达后保持等待

ammo == 0 且 pending_ammo > 0：
    停止射击、清除目标、使用移动姿态
    前往补给点 (2, 1)
    到达后等待 ammo > 0
    确认弹量增加后清除已领取的待领量并放行其他行为
```

## 节点状态

| 节点 | SUCCESS | FAILURE | RUNNING |
| --- | --- | --- | --- |
| `OutOfAmmo` | 阶段 2、存活且 `ammo==0` | 未比赛、阵亡、无数据或仍有弹 | 不使用 |
| `PendingAmmoAvailable` | 内部待领量大于 0 | 内部待领量等于 0 | 不使用 |
| `SetCombatIdle` | 已停止射击并清除目标 | 不使用 | 不使用 |
| `CollectPendingAmmo` | 裁判数据确认 `ammo>0` | XML 端口非法 | 前往补给点或在补给点等待发弹量到账 |
| `NavigateToPose` | 到达站桩点 | XML 端口非法 | 未收到定位或仍在移动 |

## 测试覆盖

- 第一分钟结束前待领量为 0。
- 剩余 360 秒时待领 100，剩余 300 秒时待领 200。
- 剩余 30 秒时累计 600，与规则书示例一致。
- 领取后清空当时已经累计的待领量。
- 后续新一分钟结束后可以再次累计 100。
- 倒计时向上抖动不会减少已累计待领量。
- 新一场比赛会重置上一场的领取历史。
- 程序在比赛中途启动时可以按照当前倒计时重建累计分钟数。
- ROS 联调覆盖无待领量站桩、新一分钟后转向补给点、到点等待、弹量到账后释放行为。

ROS 联调模式：

```bash
ros2 run decision_process test_data_publisher \
  --ros-args -p simulate_no_ammo:=true
```

## 合并约定

- 最终总树中，本任务应高于普通攻击、巡逻和追击行为，否则无弹状态下仍可能持续执行战斗导航。
- 归位、阵亡复活等全局安全行为是否高于本任务，在总树合并时统一确定。
- 本任务通过统一 `ApplyPosture` 请求移动姿态，不直接绕过姿态管理器。
- `SetCombatIdle` 在切换导航前清除射击和自瞄目标，避免沿用上一个攻击任务的输出。

## 接口边界

- 当前消息没有裁判系统直接发布的待领弹量，因此内部数值是由时间和本进程观察到的领取事件推算。
- 如果决策程序在比赛中途重启，它能恢复“理论累计量”，但无法知道重启前已经领取过几次，可能高估待领量。要彻底解决，需要新增裁判系统待领弹量字段或把领取历史持久化。
- 当前以 `ammo` 从 0 变为正数确认领取成功。如果未来允许其他途径在补给点同时增加弹量，需要增加更明确的领取成功消息。
- 站桩点是工程选择，不是规则书固定坐标；当前复用哨兵启动点。
