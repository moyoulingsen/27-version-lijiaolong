# 02 姿态切换子树 PostureManager

## 任务目标

比赛进行期间，根据其他行为子树提出的姿态请求，统一切换哨兵姿态。未提出特殊请求时保持默认移动姿态。

## 输入与输出

| 类型 | 字段 | 用途 |
| --- | --- | --- |
| 输入 | `game_period` | 仅在比赛阶段 2 执行姿态管理 |
| 输入 | `hp_sentry` | 战亡状态不执行姿态切换 |
| 输入 | `requested_posture` | 其他子树提出的姿态请求：1进攻、2防御、3移动 |
| 输入 | `cooldown_sec` | 两次实际姿态切换之间的最短时间，默认 5 秒 |
| 输出 | `posture` | 写入 `/serial_send_data.posture` |
| 输出 | `applied_posture` | 写入黑板，供其他子树读取当前实际姿态 |

## 姿态请求来源约定

姿态管理器不负责判断全部战术场景，只负责统一执行请求，避免多个行为直接争抢 `posture` 输出。

| 请求姿态 | 后续任务中的典型来源 |
| --- | --- |
| `1` 进攻姿态 | 打前哨、确认射击目标、主动攻击 |
| `2` 防御姿态 | 低血驻守、回血、需要提高生存能力的行为 |
| `3` 移动姿态 | 归位、巡逻、补给、追击和一般导航；也是默认值 |

最终合并时，所有行为只写 `requested_posture`，只有 `PostureManager` 可以写最终 `posture`。

## 子树流程

```text
PostureManager (ReactiveSequence)
├── GameRunning
└── ApplyPosture
    ├── requested_posture
    ├── cooldown_sec=5.0
    └── applied_posture
```

## 切换策略

```text
请求值不在 1..3：FAILURE
请求值等于当前姿态：保持当前姿态，SUCCESS
第一次有效切换：立即执行
距上次切换不足 cooldown_sec：保持当前姿态，等待后续 tick
冷却完成：执行切换并更新最后切换时间
```

冷却期间节点返回 `SUCCESS` 而不是 `RUNNING`，避免姿态管理器阻塞主行为树；下一次 tick 会继续检查请求。

## 节点状态

| 节点 | SUCCESS | FAILURE | RUNNING |
| --- | --- | --- | --- |
| `GameRunning` | 已收到裁判数据、阶段为 2、哨兵存活 | 非比赛阶段、数据未收到或哨兵战亡 | 不使用 |
| `ApplyPosture` | 保持、等待冷却或成功切换 | 请求值或冷却参数非法 | 不使用 |

## 规则与接口边界

`DesicionSendData.msg` 只有 `posture=1/2/3`，没有“普通/强化”标志。因此本子树只管理三种基础姿态。强化姿态如何通过裁判系统请求，需要额外通信字段或协议后才能实现，不能在当前接口中虚构。

## 独立测试

- 初始姿态为移动姿态 3。
- 第一次请求姿态 1：立即切换。
- 切换后 2 秒请求姿态 2：保持姿态 1。
- 切换后满 5 秒请求姿态 2：切换成功。
- 重复请求当前姿态：不产生额外切换。
- 请求 0 或 4：返回失败，不修改输出。
- 非比赛阶段或哨兵战亡：不执行姿态切换。

## 当前边界

- 当前独立 XML 默认请求移动姿态 3，用于验证默认行为。
- 后续子树通过黑板写入 `requested_posture` 后，才会体现不同战术场景的实际请求。
- 第一次姿态切换允许立即执行；规则只规定切换具有 5 秒冷却，未规定开局必须等待 5 秒。
